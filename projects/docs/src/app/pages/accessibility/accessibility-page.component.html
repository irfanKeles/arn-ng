Accessibility

The rules every component of the library must meet before it counts as finished, and how they are checked.

No components yet. These are rules, not a description of finished components: each component is held to them as it is added. What exists today, the ripple directive, the configuration and the theme, already follows the ones that apply to it.

  • Keyboard. Everything works with the keyboard alone: Tab and Shift+Tab, and the arrow keys, Enter, Space, Escape, Home and End as the WAI-ARIA Authoring Practices pattern for that kind of component expects.
  • Roles and states. The right role and aria-* attributes, such as aria-expanded, aria-invalid and aria-describedby. Where a native element exists, the component renders it instead of imitating it.
  • Focus. A visible focus ring. An overlay moves focus inside when it opens and back to its trigger when it closes; a dialog keeps focus inside while it is open.
  • Not color alone. A state is shown by more than a color change, and text has enough contrast in both color schemes.
  • Names and texts. Every control has an accessible name. Built-in texts, labels for assistive technology included, come from the configuration's messages, so they can be translated (Configuration).

Angular CDK's tools (FocusTrap, FocusMonitor, ListKeyManager, LiveAnnouncer) are preferred to hand-written ones. A component with an accessibility gap is not finished.

A control is never shorter than 24 CSS pixels, the minimum target size of WCAG 2.2 (success criterion 2.5.8). The floor is --arn-control-min-size in the theme, and each component writes its height with max(), so compact density cannot go below it: an xs control is 24px in both densities.

The size tokens and how they combine with density: Theming.

Keyboard focus is shown with a ring --arn-ring-width (3px) wide in the --arn-ring color. WCAG 2.2 asks a focus indicator for at least 3:1 against what is around it (success criterion 1.4.11). Against the background, the ring has about {{ ring.light }}:1 in the light scheme and {{ ring.dark }}:1 in the dark one. The light value is darker than shadcn/ui's, whose ring is below 3:1 on white.

Every animation can be turned off by the operating system's "reduce motion" setting (prefers-reduced-motion: reduce). The ripple draws no wave at all then, and reads the preference on every press. An overlay that would animate as it closes is removed at once.

Every component works right to left. Styles use logical properties, so they follow the direction of the place they are in; Stylelint rejects physical ones such as margin-left. An icon that points in a direction carries arn-rtl-mirror and is mirrored. Arrow keys that move between items follow the direction too. How to set the direction: Configuration.

Every component spec runs axe-core on what it renders and fails on any violation. The documentation's specs do the same for every page and example, in the light and dark schemes, right to left and in compact density. Keyboard behavior, focus movement and ARIA attributes have their own tests. The tests run in Chrome, without zone.js.

A fragment is scanned on its own, so axe's rule that all content must sit in a landmark is turned off for it; the pages check their landmarks separately. Each documentation page is also checked at 320px, where it must not scroll sideways.

  • Automated checks find only part of the problems. axe catches what can be decided from the page, such as missing names or low contrast; it cannot judge whether a name makes sense or a flow is usable.
  • No screen reader testing yet. Nothing has been tried with a real screen reader so far; announcements and reading order are checked only through the DOM.
  • Real key presses are not simulated. The test runner cannot scroll a region with an actual arrow key; it checks the conditions instead: the region can take focus and is the element that scrolls.
  • The ripple ignores the keyboard by design. Enter and Space activate an element without a wave; the focus ring is the keyboard's feedback.
